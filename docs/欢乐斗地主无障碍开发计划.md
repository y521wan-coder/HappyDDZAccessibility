# 《欢乐斗地主》Windows 无障碍辅助软件开发计划

版本：方案草案，2026-10-02。此文档供下一会话直接作为项目需求使用；目前没有开始开发辅助软件。

## 1. 目标、边界和目前已知事实

目标是在这台电脑上，让盲人用户借助争渡读屏和物理键盘，独立完成启动、进入普通斗地主对局、获知公开局面、选牌、出牌、过牌和结束对局。用户自己决定叫地主和出什么牌；软件负责把可见信息转成可读结构，并把用户确认过的命令送给游戏。不要读取游戏内存、网络封包或隐藏牌，也不要做自动决策或自动打牌。

目标平台是 Windows 10 IoT 企业版 LTSC 10.0.19044 x64；处理器 Intel Core i5-9400；显卡 Intel UHD Graphics 630；读屏为争渡，兼顾标准 UI Automation 的其他读屏。输入为物理键盘。游戏是腾讯 QQ 游戏大厅安装的《欢乐斗地主》客户端，当前程序 `D:\HappyDDZ\GameNew\HLDDZ3D.exe`，窗口标题显示版本 8.057.106.17343。已经通过电脑上登录的 QQ 进入游戏。游戏“设置 → 音效 → 游戏音乐”已关闭；退出设置后再次打开仍显示未勾选，说明该设置已保留，游戏音效仍开启。

本机实测：游戏窗口在 UI Automation 中显示为一个名为“欢乐斗地主”的 Pane，子控件数为 0。因而不能指望争渡直接读出牌、按钮或弹窗；游戏画面截图可取得。**尚未进入并采样实际牌桌**，所以牌面、操作流程、倒计时、不同模式和弹窗的识别准确率目前都属于尚未验证。

OCR 包位于 `D:\RapidV6_OCR\RapidV6\`，含 C++ `Rapid.dll`、头文件、9 个 ONNX 模型及 CPU/DirectML/CUDA 运行库。测试数据见 `D:\RapidV6_OCR\benchmark_results.json`：在本机 CPU、1280×720 自制文字图、模型预热后，tiny 检测 + tiny 识别三次计时的中位数为约 150 毫秒，是九种组合中最快的；tiny + small 为约 224 毫秒。此为整图文字测试，**不是牌桌实测帧率或识别准确率**。本机仅有 Intel 核显，DirectML 是否比 CPU 快尚未实测；CUDA 不适用当前硬件。RapidV6 手册默认 small + small，可以切换模型。它是调用组件，没有现成的读屏交互软件。

### 与《无障碍开发总规范》的关系

`C:\无障碍开发总规范.md` 要求桌面软件核心任务不依赖 OCR、屏幕坐标或模拟鼠标。该要求适用于我们**能控制的辅助软件自身界面**：它必须全键盘可用，向 UIA 提供名称、角色、状态、值与事件，不能靠读屏插件或图片按钮补救。此项目专门要求帮助使用一个我们不能修改源代码、且实测 UIA 无子控件的外部游戏，所以读取游戏画面必须使用 OCR/视觉识别，提交动作可能需要模拟游戏可见按钮的点击。这是外部游戏适配层的明确项目特例，不能把它说成腾讯游戏本身符合总规范。若需要整条链路完全不依赖视觉识别与模拟输入，只有腾讯在游戏源码中补全标准无障碍接口才有希望。方案完成时也只能在规定版本和已验证场景下宣称“借助辅助软件可独立游玩”，不能宣称第三方游戏原生无障碍。

## 2. 方案选择

| 路线 | 优点 | 缺点及维护成本 | 结论 |
| --- | --- | --- | --- |
| 腾讯官方为游戏加入 UIA、键盘操作及可访问登录 | 最稳定，符合总规范，没有识别延迟 | 需要腾讯配合，周期无法控制 | 长期最优，保留反馈渠道 |
| 独立桌面辅助软件：窗口捕获 + OCR + 牌面识别 + UIA 界面 + 用户确认后输入 | 可以在现有客户端上做；不改游戏文件；适配范围可逐步扩大 | 界面更新会破坏识别，截图和点击需严格校验；登录验证码等外部流程可能仍不可访问 | **推荐本项目路线** |
| 通用屏幕 OCR 热键工具 | 很快能读一部分文字 | 不知道牌局状态、牌面关系，也无法可靠选牌出牌 | 仅用于早期验证和手动求助 |
| 读屏专用插件、游戏内存/网络读取 | 有时反应快 | 与争渡绑定或涉及侵入式逆向、版本风险和游戏公平性问题 | 不作为本项目基础 |

技术栈建议：正式软件使用 **.NET 10 x64 + Windows Forms 标准控件** 构建可访问控制台式界面，调用本机 C++ RapidV6 DLL；牌面识别与窗口捕获可用原生组件封装。微软文档列出 .NET 10 对 Windows 10 LTSC/Enterprise 的支持，WinForms 标准控件有 UIA provider；仍须在这台 19044 电脑上验证具体控件与争渡输出。当前 `dotnet --list-sdks` 没列出已装 SDK；开发前需要安装或采用独立 SDK，正式交付优先发布自包含 x64 程序，不要求用户安装开发工具。备选是 C++ Win32 标准控件，运行依赖更少，但 UIA、异步状态和维护工作量更大；如果 WinForms/争渡原型出现不可修复问题再切换。**框架最终锁定以最小原型的读屏实测为门槛**。

窗口捕获首先验证 Windows Graphics Capture 的按窗口捕获；微软的 `CreateForWindow` 最低要求 Windows 10 1903，当前 19044 理论上满足。须实测窗口遮挡、最小化、缩放和游戏图形模式。如果游戏无法稳定按窗口捕获，备选前台屏幕区域截图，并在游戏被遮挡时暂停动作、明确播报原因。识别使用局部区域和变化检测，而不是每次对整屏做 OCR。OCR 返回的坐标以截图区域转换到游戏客户区，窗口移动和 DPI 缩放后重算。

## 3. 产品结构

1. **窗口与捕获层**：按进程和窗口标题识别当前游戏窗口；读取客户区尺寸、DPI、前后台与遮挡状态；捕获画面，检测黑帧、卡帧、窗口重建及版本变化。只处理游戏窗口，不长期保存全屏照片。
2. **识别层**：RapidV6 识别文字和坐标；针对手牌、牌桌和对手已打出的牌，另做牌面图像模板或小型分类器。牌角的数字/字母可由 OCR 辅助校验，但花色、王、重叠牌和选中状态不能只靠文字 OCR 猜。记录每项的区域、置信度、时间戳与相互校验结果。
3. **牌局状态层**：把连续帧整理成有限状态机，例如大厅、模式选择、匹配、叫地主/抢地主/加倍、本人回合、他人回合、结算、弹窗、未知。仅在多帧一致且满足合法状态转换时更新。维护手牌多重集合、地主身份、上下家方位、上轮牌型、剩余张数、轮到谁及倒计时。界面异常时进入“识别暂停”，绝不凭旧状态出牌。
4. **可访问交互层**：独立窗口提供标准控件和 UIA 信息；读屏用 Tab/方向键浏览，必要时用可配置快捷键快速读取状态。关键状态变化写入可回看的事件列表，避免语音覆盖和频繁抢焦点。辅助软件不能把识别文字画到图片上作为唯一输出。
5. **动作层**：把“选择第 N 张/某点数牌、取消选择、出牌、过牌、叫地主、关闭弹窗”等用户命令转换为可见目标的输入。动作前验证窗口、当前回合、牌面和按钮仍然匹配；动作后重新截图确认游戏已经接受。若不确定，报告失败并停下，不连续重试点击。涉及金币、钻石、购买、充值、道具消耗的按钮默认不接管。
6. **配置与诊断层**：模式、窗口大小、识别阈值、按键映射、OCR 模型、播报频率、隐私设置有可访问表单。保存配置原子写入并可备份/重置。诊断日志只记状态和错误，不记 QQ 密码、验证码、登录令牌；截图留存默认关闭，由用户主动启用并可一键清除。

## 4. 用户实际操作路径

以下为拟定键位，需先与争渡快捷键核对，发现冲突就调整；所有命令在软件窗口也有可聚焦按钮，热键不是唯一入口。

| 任务 | 键盘路径和读屏反馈 | 异常与退出路径 |
| --- | --- | --- |
| 启动及连接 | 启动辅助软件；主窗口读“未连接/正在连接/已连接欢乐斗地主”；Tab 到“连接游戏”按 Enter | 未找到游戏时给出启动入口与“重试”；Esc 不误关整个软件 |
| 进入普通对局 | 在辅助软件“游戏导航”选项卡，用方向键选择“普通斗地主/可用场次”，Enter 后先朗读场次规则和可能花费，再确认 | 未识别场次或收费内容则禁止自动进入，允许返回和重扫 |
| 查询局面 | “当前局面”区域读本人身份、轮次、剩余时间、三个玩家剩余牌数、上轮牌型和出牌者；按“重新读取”更新 | 识别不一致时读“状态不确定”，保留上次确认时间，不假装是当前局面 |
| 浏览手牌 | 聚焦“手牌”列表；方向键逐张或按点数分组浏览，读“第 4 张，红桃 10，未选中”；Space 切换选中；Home/End 到两端 | 手牌数量不符、牌角被遮挡或图案陌生时禁止出牌并提示重扫 |
| 出牌 | 选牌后到“出牌”按钮，先读“将出：一对 10”；Enter 后可设二次确认；仅本人回合且游戏确有可用按钮时执行，再读“已出/游戏拒绝/未确认” | 出牌失败不自动再次点击；可清空选择、重扫和查看原因 |
| 过牌与叫地主 | 对应控件仅在合法阶段启用，读清当前行为和倒计时，Enter 提交并回读结果 | 超时或阶段切换时禁用旧动作并报“回合已变” |
| 对手出牌与结算 | 状态区域简短通知“上家出单张 K”；可用“事件记录”回看。结算页读输赢、剩余牌、影响金币和返回入口 | OCR 无法确认金额时明确说“不确定”，不进行消费或二次操作 |
| 设置、帮助、退出 | Tab 到设置；标准复选框、组合框和说明；Esc 关闭弹窗并回到触发控件；退出有保存状态反馈 | 崩溃重启后报告配置是否恢复；绝不抢占游戏/读屏焦点循环播报 |

大厅促销、公告、背包、商城、签到、更新提示和安全验证都可能阻断进入牌局。要把每类遮挡识别成“可读标题、关闭/返回或继续”的任务，未知弹窗暂停所有游戏输入；**登录与验证码若只能看图且没有腾讯提供的可访问替代方式，则不能把首次独立登录宣称为已解决**。已经登录的 QQ 会话可作为当前测试起点，但需单独标记这一限制。

## 5. 识别和动作的具体策略

- **先采样再适配**：截取已授权测试中各阶段的窗口画面，建立匿名图片集和人工标注：区域、文字、手牌每张牌、按钮、倒计时、选中态、弹窗。覆盖 2D/3D 外观、窗口大小、DPI、动画、遮挡、不同牌背和游戏更新。样本中如有头像或账户信息，裁切或模糊处理。
- **分层识别**：固定结构先用锚点与相对布局找到游戏客户区、手牌区和按钮区；文字区域跑 tiny+tiny OCR，低置信度或关键数据不一致时重试 tiny+small/small+small；牌图用模板/分类器+OCR 双重校验。布局模型只在普通 OCR 无法确定结构的页面调用，不在每帧使用。
- **时序校验**：同一场景至少两帧一致才更新关键状态；用发牌前后张数变化、出牌后手牌减少、轮次转移、按钮状态和倒计时交叉核对。不能从对手剩余张数推断隐藏牌；只读用户可见信息。
- **性能策略**：局面无变化时低频采样；轮到本人且倒计时存在时提高采样；只对变化的 ROI 识别。OCR 在线程中串行调用（RapidV6 单实例冲突返回 `BUSY`），UI 线程绝不等待推理。必要时优先完成手牌/按钮识别并跳过装饰文字。先分别基准 CPU 和 DirectML，选择本机真正更快更稳的后端。
- **输入校验**：用当前截图重新定位目标并验证其可点击；窗口不是前台、缩放变化、目标与上一帧不符、检测到商店/收费弹窗或 OCR 过期时直接拒绝。动作执行一次后等待可见反馈，失败时让用户选择重试。坐标属于适配器内部，用户永远不需要知道或手动输入。
- **支持性**：按游戏版本保存独立识别配置；更新后检测布局指纹，不符就停止自动输入、仍可尝试只读 OCR，并提示需要适配。提供导出匿名诊断包的明确开关，便于后续修复。

## 6. 实施阶段与交付门槛

| 阶段 | 开发内容 | 必须展示的可检查结果 |
| --- | --- | --- |
| 0. 现场摸底 | 进入不花钱的普通牌局，录制/截取关键画面；核对规则、游戏内键盘能力、窗口捕获、UIA/MSAA 和争渡输出；评估登录阻断 | 场景清单、截图样本、键盘/读屏观察、花费与风险清单；明确哪些路径无法继续 |
| 1. 可访问壳程序 | WinForms 主窗口、设置、事件记录、状态区域、焦点恢复和完整键盘路径；接入真实/模拟数据 | 争渡真人可独立操作基本界面；UIA Inspect/Accessibility Insights 核对名称、角色、状态、事件 |
| 2. 只读牌局助手 | 捕获游戏窗口，接入 RapidV6，识别模式、手牌、对手出牌、剩余张数、倒计时和弹窗；不提交动作 | 用录制样本及实时牌局核对准确率、延迟和未知状态处理；用户可完整听懂一局牌 |
| 3. 用户控制动作 | 手牌选择、取消、出牌、过牌、叫地主/抢地主及常见弹窗关闭；每步回读结果并允许撤销未提交选择 | 用户全程键盘完成若干真实普通对局，无错误出牌或误入收费入口 |
| 4. 稳定与覆盖 | 处理窗口移动/缩放、不同牌型、断线重连、结算、多类弹窗、游戏版本变化；安装与卸载流程 | 回归报告、错误恢复、独立启动包、可访问帮助和决策日志 |

建议先交付阶段 0 的结论，再决定是否继续投入完整实现；这是为了验证关键技术是否能支撑“独立游玩”。阶段 1—4 的时间不能在未看过真实牌桌、弹窗和实际读屏前可靠估算。每阶段完成即做一次争渡+物理键盘真人测试，不等项目末尾补测。

## 7. 测试与验收

1. **功能矩阵**：发牌、叫地主/抢地主/加倍（若实际模式存在）、本人出牌、过牌、对手出牌、结算、返回大厅、断线重连、常见公告与未知弹窗。覆盖单张、对子、三张、三带、顺子、连对、飞机、四带、炸弹、王炸，以及牌手重叠和同点数不同花色。规则以实际游戏模式为准。
2. **识别量化**：用人工标注的独立截图集计算整手牌完全正确率、每张牌正确率、牌型和按钮状态准确率；不能只展示几张成功图片。关键动作要求“零未确认点击”；任何不确定的牌或阶段必须进入安全暂停。性能报告分捕获、OCR、牌识别、状态整理和播报延迟；在倒计时最短场景也要留出用户思考与操作时间。
3. **真实任务**：盲人用户开启争渡，用物理键盘从已登录状态独立进入至少 20 局不同牌况的普通对局，并能完成或安全退出。每局记录错误、卡住原因和是否需要他人或视觉协助。把“首次登录”单独测试；若验证码没有可访问替代方案则标为未通过，而不是忽略。
4. **无障碍检查**：所有辅助软件控件用标准 UIA 提供名称、角色、状态和值；Tab/Shift+Tab、方向键、Enter、Space、Esc 可完成核心任务；弹窗焦点进入/返回正确；状态变化不过度打断争渡；事件可回看；快捷键可关闭/修改。再用 NVDA 做兼容复核。无真人读屏测试的结果只能写“代码级检查通过，真人读屏未验证”。
5. **鲁棒性**：游戏更新、分辨率与 DPI 改变、窗口遮挡/最小化、OCR 空结果、画面动画、配置损坏、模型缺失、GPU 回退、网络断开、焦点被其他程序夺走，都必须停在可解释、可恢复的状态；不能向错误窗口送输入。
6. **发布流程**：安装、首次启动、更新、回滚、卸载均可读屏和键盘完成；留存哪些配置需说明。交付安装包、源码、模型来源/许可证清单、键盘说明、测试矩阵、已知限制和回退方法。不得把账户秘密、截图或日志打进安装包。

完成标准不是“能识别一些字”，而是用户在已定义范围内能独立、可预测地完成整局。若任何核心路径需要人看图帮忙，就明确写限制，不能声称“完全无障碍”。

## 8. 主要风险与备用方案

| 风险 | 失败表现与代价 | 处理和备用方案 |
| --- | --- | --- |
| 游戏自绘和频繁更新 | 牌面或按钮位置变化，可能错误点击 | 版本/布局指纹校验，更新后只读暂停；样本回归后再放开输入；推动腾讯提供官方接口 |
| 手牌重叠、动画、特效 | 看错牌导致错误出牌 | 多帧、多尺度牌图识别；逐张可读复核；不确定则禁用出牌并提示重新扫描 |
| 捕获黑屏或窗口被遮挡 | 旧画面被当成当前局面 | 帧时间戳、黑帧/卡帧检测；停用输入；切换经验证的前台捕获 |
| OCR 速度与倒计时 | 状态播报太迟，错过回合 | ROI、变化检测、tiny 优先、异步线程；必要时只播报关键状态；若仍不够快，标明该模式不支持 |
| 登录验证码、特殊活动弹窗 | 无法独立进入游戏或回到牌桌 | 先测试腾讯官方可访问登录选项；使用已有 QQ 登录仅作阶段性起点；无法解决时不能宣称完整独立启动 |
| 误入收费或策略自动化 | 金币损失或不符合用户意愿 | 默认禁用购买/充值/自动决策；花费前读清金额并独立确认；不自动重试点击 |
| 争渡兼容或焦点冲突 | 读不到信息、按键无响应 | 标准控件/UIA 事件优先，快捷键可改；最小原型提前真人验证；必要时切换 UI 框架 |

## 9. 当前假设、需用户决定的事项和下一会话起点

当前假设：先支持 QQ 游戏大厅 Windows 客户端、已登录 QQ、普通斗地主对局；不覆盖网页/手机端；不代替用户做出牌策略；所有游戏内购买默认禁用；目标是陪同明眼人公平游玩。未知项包括是否需要 2D/3D 两种牌桌、是否允许辅助软件在本人确认后模拟点击、是否需要好友房/比赛/癞子玩法、是否必须从完全退出 QQ 后独立登录。以上会影响范围，但现阶段无需改变电脑设置或投入购买。

下一会话建议按阶段 0 启动：先读本文和 `C:\无障碍开发总规范.md`，核对当前游戏及 OCR 目录，询问/记录用户最常玩的模式，然后在不花费虚拟货币的情况下实测牌桌、争渡和捕获技术。阶段 0 出具可行性与阻断点，再锁定框架和后续开发范围。若用户认可本计划，即视为同意按此方向做可逆原型；购买、对外发布或改变高成本技术路线另行展示具体结果供决定。
