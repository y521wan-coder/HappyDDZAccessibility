# 无障碍软件开发总规范（AI 强制执行版）

版本：1.0  
更新日期：2026-08-29  
用途：本文件与具体项目需求、代码仓库和测试环境说明一起交给 AI、开发者或测试人员，作为设计、选型、编码、修改、重构和交付时的强制要求。

---

## 0. 使用方法与最高优先级指令

### 0.1 给 AI 的直接指令

收到本文件后，你必须把它视为项目需求的一部分，不需要用户再次解释什么是读屏、焦点、键盘操作或无障碍树。无论任务是新建软件、修改代码、修复错误、增加功能、重构界面、替换框架、制作安装器还是生成文档，本文件均自动生效。

你必须先判断本次改动会影响哪些用户界面和任务流程，再同步实现功能与无障碍。不得先完成视觉或鼠标交互，最后再“补标签”。不得用 OCR、屏幕坐标、模拟鼠标、读屏标签、读屏路标、读屏插件或专用补丁掩盖产品本身的缺陷。

在开始编码前，先输出以下内容：

1. 产品类型、目标平台、最低系统版本、主要读屏或辅助技术、输入方式和实际测试环境。
2. 本次功能涉及的窗口、页面、弹窗、列表、表单、通知和核心任务。
3. 每个核心任务的无障碍操作路径：桌面和网页写出纯键盘路径；移动端写出读屏线性导航、标准激活、自定义操作和返回路径。
4. 技术栈、控件库、WebView、安装器及第三方组件如何提供标准无障碍信息；没有证据时明确写“尚未验证”，不得凭印象声称兼容。
5. 项目特有风险、最可能失败的位置、失败代价和备用方案。
6. 需要用户决定的不可逆选项，以及当前所有重要假设。

完成后必须提交：实际修改、自动检查结果、真人读屏测试结果、未测试项、已知限制、键盘或手势说明和决策日志。无法亲自运行目标读屏时，只能写“代码级检查通过，真人读屏未验证”，不得伪造验收结果。

### 0.2 不可降低的核心目标

用户必须能够独立、完整、可预测并且高效地完成任务：

- 找得到功能，知道自己在哪里；
- 听得懂对象是什么、当前值和状态是什么；
- 知道可以执行什么操作以及操作后的结果；
- 不因焦点丢失、乱跳、隐藏或被后台抢走而迷路；
- 不依赖视力、他人协助、OCR 或读屏补丁；
- 不因每个列表项出现大量重复焦点而失去浏览效率；
- 在成功、失败、等待、取消、超时和状态变化时及时得到适量反馈。

“能读到一些文字”不等于无障碍。只有真实任务能够完成，才算通过。

### 0.3 要求等级

- **必须**：缺少即验收失败。
- **禁止**：出现即验收失败。
- **应当**：无充分、可验证理由时必须实现；确实不能实现须在编码前说明影响和替代方案。
- **可选**：只能在不破坏基础无障碍和兼容性的前提下采用。

### 0.4 规则冲突处理

具体项目要求比本文更严格时执行更严格者。平台惯例不同于本文通用表述时，采用该平台的标准无障碍行为，但必须保留等价任务能力。确需偏离强制项时，先说明原因、影响、标准方案和替代方案，取得用户明确同意后再实施。

## 1. 适用范围与默认测试基线

### 1.1 适用产品

本规范适用于：

- Windows、macOS 和 Linux 桌面软件；
- Android、iOS 和 iPadOS 应用；
- 网站、Web 应用、PWA、桌面或移动 WebView；
- 安装、首次启动、登录、更新、修复、迁移、卸载和崩溃恢复程序；
- 命令行工具、远程 SSH 工作流和必须使用终端的管理工具；
- 服务器产品的管理网页、桌面客户端、移动客户端、CLI、日志、报告和 API 文档；
- 软件展示、导入或导出的文档、数据、图片、图表和媒体。

纯后端服务内部实现不要求提供读屏界面；但只要有人直接操作管理后台、客户端、CLI、安装脚本、监控页面或文档，这些接触面就适用本规范。

### 1.2 用户当前 Windows 硬性基线

除非具体项目另有说明，用户当前电脑环境为：

- Windows 10 IoT 企业版 LTSC，版本 10.0.19044，x64；
- 主要读屏：争渡；
- 网页浏览器：Google Chrome；
- 桌面和网页验收：物理键盘，全程不使用鼠标、模拟鼠标、OCR、标签或路标补救。

当前 Windows 10 环境是 Windows 项目的最高兼容优先级。不得把 Windows 11 专属 API、控件、运行时或安装方式作为核心功能的唯一实现。选型时必须以目标版本的官方支持范围和真实运行结果为证据；自动更新的运行时、WebView 或依赖不得更新后突然放弃该系统。

争渡是用户环境中的强制人工测试读屏，但实现必须基于 UI Automation、网页无障碍树等标准接口，不得加入妨碍 NVDA、保益或其他辅助技术的争渡专有依赖。

### 1.3 其他平台的项目基线

Android、iOS、iPadOS、macOS 和 Linux 项目开始前必须补充实际设备或系统版本、读屏版本、输入设备、应用语言、屏幕方向和是否使用外接键盘。未提供时 AI 可以先做可逆的代码分析和草案，但不得自行把某个版本假定为最终验收基线。

建议的主要人工测试组合为：

| 平台 | 主要读屏或辅助技术 | 必测输入方式 |
|---|---|---|
| Windows | 争渡；标准接口兼顾 NVDA 等 | 物理键盘 |
| Web | Windows 上的争渡 + Chrome | 物理键盘、读屏浏览与编辑模式 |
| Android | TalkBack | 触摸读屏手势；项目支持时测试外接键盘；复杂操作兼顾 Switch Access |
| iOS/iPadOS | VoiceOver | VoiceOver 手势；项目支持时测试外接键盘和 Full Keyboard Access |
| macOS | VoiceOver | 键盘、VoiceOver 命令 |
| Linux | Orca 或用户指定读屏 | 键盘；明确发行版、桌面环境和工具包 |

移动端的“可访问”不是禁止触摸，而是禁止依赖未经辅助技术解释的精确点按、坐标定位、连续拖拽、视觉路径或只有健视用户才能发现的手势。核心任务必须可通过读屏焦点、标准激活、可发现的无障碍操作及明确返回路径完成。

## 2. AI 协作知情权与决策规则

### 2.1 岔路口必须披露

遇到真实的技术岔路口时，AI 不得只给用户一条路。若存在平台标准方案、成熟组件、主流库、商业成品和自制方案，必须给出对比，至少包括：

- 标准或搜索名称；
- 支持的目标系统和无障碍接口；
- 成本、开发复杂度、可靠性、可测试性和长期维护；
- 对读屏、键盘、焦点、性能和安装体积的影响；
- 最可能的失败点、失败代价和 B 计划；
- 推荐方案及理由。

不得因为用户不熟悉术语而省略成熟方案。引入概念、工具或模式时，同时给出行业标准名称或可独立搜索的关键词。

### 2.2 可逆与不可逆决策

- **不可逆或高迁移成本决策**：购买服务、删除数据、对外发布、锁定框架或数据库、替换核心 UI 技术栈、放弃旧系统、改变文件格式或升级后无法回退。必须先展开选项并等待用户确认。
- **可逆决策**：写草稿、增加局部测试、尝试参数、创建可撤销的小范围修复。可直接执行，完成后说明。
- 无法判断时按不可逆处理。

该规则不要求 AI 为每个变量名或常规代码细节暂停；只有会实质改变成本、兼容性、数据或后续路线的选择才需要用户拍板。

### 2.3 假设、证据和决策日志

关键节点必须列出假设，并允许用户否决。事实应标明证据层级：官方支持、真实实测、自动检查、代码推断或尚未验证。

每个重要选择记录一行：

> 决策：选择 X；未选择 Y；原因 Z；影响范围 A；回退方式 B。

用户询问“哪些是土办法”“有没有标准方案”或类似问题时，必须完整列出当前所有自制、非标准、读屏专用或依赖补丁的部分、行业标准替代和迁移成本。

### 2.4 出错后的修复

发现此前漏掉重要方案、错误声称兼容、遗漏无障碍路径或导致用户走弯路时，必须直接说明错误、影响和原因，补全方案地图并给出修复步骤。不得淡化成“体验优化建议”。

## 3. 跨平台强制设计原则

### 3.1 标准语义优先

优先使用平台标准控件、语义 HTML 和经过验证的组件。每个有意义的对象必须在平台无障碍树中正确出现；装饰对象应隐藏。每个交互控件必须提供：

- 准确、简洁、可本地化且在上下文中可区分的名称；
- 与真实行为一致的角色或控件类型；
- 当前状态，例如选中、按下、展开、禁用、只读、必填、无效、忙碌；
- 当前值、范围、单位、位置和必要说明；
- 支持的标准操作；
- 与标签、说明、错误、标题、行列头等对象的程序化关系；
- 状态和内容变化对应的标准无障碍事件。

角色是一种行为承诺。把对象标成按钮、复选框、选项卡、树或网格后，必须同时实现该类型应有的键盘、手势、状态和事件，不能只改名称或角色。

### 3.2 名称、说明和值

- 图标按钮、图片按钮、Unicode 符号和字体图标必须有文字名称。
- 同一上下文中的同名按钮必须补充对象范围，例如“删除：会议记录”，但不要重复读屏已经可靠提供的上下文。
- 占位符、颜色、位置和工具提示不能作为唯一标签。
- 控件名称描述“它是什么”，提示描述“如何或为何使用”，值和状态描述“现在怎样”；不得把长说明全部塞入名称。
- 不要在名称中重复读屏会自动播报的类型，例如通常写“发送”，不写“发送按钮”。
- 图片内的重要文字必须另提供真实文本；OCR 或 AI 图片描述只能是用户主动启用的辅助功能。

### 3.3 主操作与次级操作

常用主操作应当是控件的默认激活行为或直接可达的主要控件。复制、转发、引用、删除、移动、置顶等针对当前对象的次级操作，可使用平台原生“自定义无障碍操作”集中暴露，避免每个列表项增加大量重复焦点。

自定义操作必须遵守：

1. 不改变原主操作；操作名称必须准确说明执行结果。
2. 调用与可视菜单、手势或按钮相同的业务逻辑，不能维护两套结果不同的代码。
3. 根据当前对象和权限动态提供；不可用的动作应移除或明确禁用原因。
4. 列表复用后不得残留上一项操作、重复堆积或作用于过期位置。
5. 执行后报告结果，并保持或恢复到合理焦点。
6. 删除、付款、发布等高风险动作仍需可访问的确认和撤销机制。
7. 不得把核心任务只藏在不易发现的自定义操作中；首次使用、帮助或读屏提示应说明“有操作可用”。

### 3.4 导航效率

- 读屏线性导航顺序必须符合任务逻辑。
- 静态装饰、重复图标和无独立意义的内部子元素不得制造多余焦点。
- 也不得把包含多个独立任务的大区域粗暴合并为一个无法操作的焦点。
- 长列表、数据网格、树和多窗格界面必须提供结构、边界、当前位置、总数或可用的快速定位方式。
- 在不牺牲功能发现性的前提下，减少完成高频任务所需的按键、滑动和菜单层数。

### 3.5 焦点管理

- 任意时刻的交互焦点必须指向无障碍树中存在、可见、未被销毁且有名称的对象。
- 加载、刷新、筛选、排序和局部更新不得无故把焦点移到窗口开头、浏览器地址栏、后台或未知对象。
- 删除当前项后，焦点移到下一个项目；没有下一个时移到上一个；列表为空时移到列表标题、空状态或新增按钮。
- 新页面或主要区域出现时，报告标题并把焦点放到有意义且可预测的位置。
- 不得用移动焦点来强行朗读普通通知，也不得定时抢焦点。
- 虚拟化列表中，获得焦点的项目不能在操作过程中被回收成其他内容。

### 3.6 弹窗、菜单和浮层

- 弹窗必须有名称、正确模态语义和可读说明。
- 打开时焦点进入弹窗的首个合理位置；背景不可操作；关闭后返回触发控件或合理邻近位置。
- 标准取消键或返回操作必须有效。桌面和网页通常使用 `Esc`；Android 使用系统返回；iOS 使用可发现的关闭控件并支持适用的逃逸操作。
- 菜单、下拉列表、自动完成和底部面板打开、关闭、当前项和数量必须可知。
- 临时浮层不得让读屏焦点落在视觉存在但无语义的空白区域。

### 3.7 状态、进度与通知

- 操作后必须能判断：尚未开始、已接受、处理中、成功、失败、已取消、部分成功或需要额外输入。
- 已知进度报告百分比、数量或阶段；未知进度报告“正在处理”并在结束时明确通知。
- 不用旋转图、闪烁、颜色、震动或声音作为唯一信息。
- 高频进度必须节流，避免连续打断读屏；重要结果应可再次查看。
- 优先更新控件状态、值、标题、标准状态区域或无障碍事件。命令式朗读 API 只能在没有更合适语义时作为补充，不得重复正常朗读或成为关键信息唯一来源。
- 可取消任务提供可达的取消操作，并说明取消后是否保留部分结果。

### 3.8 表单、错误与验证

- 每个字段有程序化标签；必填、格式、单位和示例在输入前可得知。
- 提交失败时提供错误汇总和字段级错误，二者都要与相应字段关联。
- 不清除其他正确内容；把焦点移到首个错误时要可预测，并允许依次找到全部错误。
- 错误信息说明问题、可能原因和可执行的修正方式，不能只写“失败”“无效”或错误代码。
- 身份验证和验证码必须提供无需看图、听辨模糊声音或求助他人的可访问方案。

### 3.9 拖拽、手势和位置操作

任何拖放、滑动删除、长按菜单、画线、调整顺序或依赖路径的操作，都必须有离散的等价操作。例如：

- “上移”“下移”“移到开头”“移到末尾”；
- “选择起点”“选择终点”“确认移动”；
- “增加”“减少”或可直接输入数值；
- “打开操作菜单”“删除”“归档”。

操作完成后报告对象的新位置、值或状态。不得要求盲人用户通过屏幕坐标猜测目标。

### 3.10 时间、自动变化和中断

- 超时前提前通知并允许延长；安全原因不能延长时说明剩余时间和后果。
- 自动轮播、自动刷新、自动播放和倒计时不得持续抢占读屏。
- 自动更新内容要能暂停、控制或改为按需刷新；紧急通知与普通状态采用不同打断级别。

### 3.11 安全和隐私

- 密码框报告密码角色，但不朗读、记录或复制其内容。
- API 密钥、令牌、恢复码和隐私数据不得出现在普通通知、日志、崩溃报告或自动朗读中。
- 显示、复制或导出秘密必须由用户明确执行，并说明风险和结果。
- 删除、覆盖、付款、发布、批量修改和退出未保存内容时，确认框必须说清对象、数量、金额或影响范围，不能只问“是否确定”。

## 4. 桌面与网页的键盘标准

### 4.1 通用键盘要求

桌面软件和网页的所有功能必须用物理键盘完成，不得要求鼠标、模拟鼠标或屏幕坐标。鼠标单击、双击、右击、悬停和拖放必须有等价键盘入口。

- `Tab` / `Shift+Tab`：在控件或主要区域之间前后移动。
- 方向键：在菜单、列表、树、选项卡、单选组、组合框、工具栏和网格内部移动。
- `Enter`：激活链接、默认命令或平台惯例规定的操作。
- `Space`：操作按钮、复选框、开关或选择项。
- `Esc`：关闭菜单或可取消弹窗、取消当前临时模式。
- `Home`、`End`、`Page Up`、`Page Down` 和带修饰键的方向键：遵循所在控件和平台惯例。

不得随意改变标准按键含义。快捷键不得与操作系统、浏览器、读屏和常见文本编辑命令明显冲突；全局快捷键应可修改或关闭。自定义快捷键必须在菜单、帮助或设置中可查，同一功能仍要有普通控件或命令入口。

网页不得把无修饰的单字母快捷键作为核心功能唯一入口，因为它会与读屏的字母导航冲突。

### 4.2 焦点顺序与复合控件

`Tab` 应在组件之间移动，方向键在复合组件内部移动。不要让工具栏中的每个按钮、单选组中的每个选项或大型网格中的每个单元格都无条件进入全局 Tab 顺序。复合控件必须采用平台标准的内部焦点管理，并清楚区分“当前焦点”和“已选择”。

禁止正数 `tabindex` 排序、键盘陷阱、隐藏焦点和没有退出说明的特殊编辑模式。

## 5. Windows 桌面软件专项要求

### 5.1 技术接口与选型

Windows 应优先使用能在目标 Windows 10 上运行的标准控件，并通过 Microsoft UI Automation（UIA）提供信息。MSAA 只作为旧框架兼容层；新自定义控件不得仅依赖读屏私有接口。

自定义控件必须暴露与行为匹配的 UIA Control Type、属性、Control Pattern 和事件。例如：

- 按钮：`Invoke`；
- 复选框、开关：`Toggle`；
- 组合框、树节点：`ExpandCollapse`；
- 列表：`Selection` / `SelectionItem`；
- 编辑器：`Text` 或 `Value`；
- 数值控件：`RangeValue`；
- 表格：`Grid` / `Table`，并建立行列标题关系；
- 虚拟化项目：正确支持虚拟化和项目实现，不得让屏外项目变成空白或错位对象。

选择 .NET、Win32、WPF、WinForms、WinUI、Qt、Electron、Tauri 或其他框架时，必须验证具体版本在 Windows 10 19044 的运行支持和 UIA 输出。框架“支持无障碍”的宣传不能代替控件级实测。

### 5.2 窗口与控件

- 主窗口、子窗口和对话框有明确且随内容更新的标题。
- 菜单栏、工具栏、状态栏、内容区、导航区和侧栏结构清楚；多窗格可用 `F6`、`Ctrl+Tab` 或平台惯例切换并报告名称。
- 列表报告项目名称、选择状态、位置和总数；多选方式符合 Windows 惯例。
- 树报告层级和展开状态，支持左右键展开、折叠和移动层级。
- 选项卡报告名称、位置和选中状态，支持方向键或 `Ctrl+Tab`。
- 表格提供表名、行列标题、单元格值、行列位置和排序状态。
- 编辑框支持光标、选区、逐字逐行、复制粘贴、只读和密码状态。
- 组合框、滑块和数值框报告值、范围、单位、步长以及展开或可编辑状态。
- 托盘窗、悬浮窗、无边框窗和自定义标题栏不得造成焦点不可达；后台窗口不得抢焦点。

### 5.3 文件与系统流程

优先使用标准打开、保存和文件夹选择对话框。自定义文件管理器不得降低路径输入、文件名编辑、过滤、排序、位置切换和错误反馈能力。覆盖、永久删除和批量修改前说明范围；结束后报告数量、保存位置和失败原因。

## 6. 网站、Web 应用与 WebView 专项要求

### 6.1 合规基线

网站和 Web 应用以 WCAG 2.2 AA 为最低合规基线，并满足本文件中更严格的盲人独立使用要求。WAI-ARIA APG 是复杂组件键盘模式的重要实现参考，但不是用 ARIA 代替正确 HTML 的理由。

### 6.2 结构与语义

- 页面有准确、唯一并随路由更新的标题。
- 使用主内容、导航、搜索、页眉、页脚等路标；标题按逻辑层级组织，不为视觉大小伪造层级。
- 列表用列表元素，数据表用原生表格，按钮用 `button`，导航链接用有效 `a`。
- 禁止只绑定点击事件的 `div` / `span` 伪装按钮。
- 输入框使用程序化 `label`；说明、格式和错误用 `aria-describedby` 等正确关系关联。
- ARIA 只补足原生 HTML 缺少的语义；添加角色不会自动获得键盘行为。
- Canvas、WebGL、图片式界面和复杂 SVG 必须另有结构化、可操作的 DOM 等价界面。

### 6.3 动态界面

- 单页应用路由变化时更新标题，报告新页面，并把焦点放到新页面标题、主内容或合理的任务起点。
- `dialog` 有可访问名称、模态语义、初始焦点、焦点约束和关闭后焦点恢复。
- 保存、搜索、加载、错误和结果使用适当的 `status`、`alert` 或 live region；`assertive` 仅用于必须立即处理的紧急信息。
- 局部刷新保持阅读或操作位置。无限滚动提供项目边界、加载反馈、快速定位以及分页或等价替代。
- 自动完成报告展开状态、结果数量和当前选项，并允许键盘选择和退出。
- 不可访问的日期、时间、颜色或富文本选择器必须有标准文本输入或等价入口。

### 6.4 复杂组件

自定义菜单、组合框、列表框、树、网格、工具栏和选项卡必须遵循对应 WAI-ARIA APG 模式的角色、状态、关系、键盘和焦点管理。若现有成熟组件已经经过目标浏览器与读屏验证，应优先评估成熟组件；若自制，必须说明维护和兼容成本。

WebView 必须把内部内容暴露为与目标浏览器相当的无障碍树。不得把整页呈现为“未知”、图片、画布或一个无法进入的容器。原生层与 Web 层切换时焦点不能丢失。

### 6.5 Chrome + 争渡实测

必须验证：

- `Tab` / `Shift+Tab` 到达全部可交互元素；
- 方向键连续阅读普通文本；
- 浏览模式与编辑模式的进入、输入和退出；
- 标题、按钮、编辑框、组合框、复选框、单选框、图片、列表、表格、链接和路标能被对应导航找到；
- 返回、前进、路由变化、弹窗、菜单和局部刷新后的焦点位置；
- 没有必须依赖鼠标或视觉才能发现的操作。

## 7. Android 应用专项要求

### 7.1 基础语义

优先使用 Android 系统、AndroidX、Material 和 Jetpack Compose 的标准组件。Views 界面通过 `AccessibilityNodeInfo` 节点、属性、操作和事件提供信息；Compose 通过 Semantics tree 提供信息。

- 文本按钮通常依靠可见文本命名；只有图标或非文本图像需要准确的 `contentDescription`。
- 装饰图片的描述应为 `null` 或从无障碍树排除，避免读出“图片”。
- 不能把整张卡片所有文本无条件拼成冗长 `contentDescription`，从而丢失文本结构和操作语义。
- 选中、展开、开关、错误、进度和自定义状态使用相应语义或 `stateDescription`，不得只改图片和颜色。
- 标题、集合、列表项位置、窗格和错误应使用框架提供的标准语义。
- 触控目标原则上不小于 48dp；视觉目标较小时可扩大可点击区域，但不得造成重叠焦点。

### 7.2 自定义无障碍操作（Accessibility Actions）

消息、文件、订单等列表项的默认激活用于最主要操作，例如“打开详情”。复制、转发、引用、删除、归档、置顶、上移和下移等次级功能应优先评估自定义无障碍操作，避免每项后出现大量重复焦点。

Views 可使用 `ViewCompat.addAccessibilityAction`，或在需要完全控制和动态更新时使用 `AccessibilityDelegateCompat` 填充节点并处理操作。Compose 使用 `Modifier.semantics { customActions = ... }` 或相应标准 API。

这些动作应通过 TalkBack 的当前对象操作菜单或“操作”阅读控制项被发现和执行。TalkBack 手势允许用户自定义且会随版本变化，代码和帮助不得把某一个固定手势当成唯一入口；验收对象是动作能否由标准节点操作被读屏发现、选择和正确执行。

Views 简化示例：

```kotlin
ViewCompat.addAccessibilityAction(messageView, "复制") { _, _ ->
    copyMessage(messageId) // 与可视菜单调用同一业务函数
    true
}

ViewCompat.addAccessibilityAction(messageView, "删除") { _, _ ->
    requestAccessibleDeleteConfirmation(messageId)
    true
}
```

Compose 简化示例：

```kotlin
Modifier.semantics(mergeDescendants = true) {
    customActions = listOf(
        CustomAccessibilityAction("复制") {
            copyMessage(messageId)
            true
        },
        CustomAccessibilityAction("删除") {
            requestAccessibleDeleteConfirmation(messageId)
            true
        }
    )
}
```

若界面仍显示相同操作的独立图标按钮，可在确认父项自定义操作完整、非读屏用户仍能操作，并完成 TalkBack、Switch Access 和 Voice Access 验证后，谨慎合并或清理重复子语义。不得为了减少 TalkBack 焦点而让其他辅助技术失去功能。

### 7.3 RecyclerView 和动态列表

`RecyclerView.ViewHolder` 会复用，禁止在每次绑定时无条件反复追加动作。必须保证：

- 每次初始化节点时根据当前 `bindingAdapterPosition`、对象 ID、权限和边界动态生成动作；
- `NO_POSITION` 或项目已删除时拒绝执行；
- 上移第一项时不提供“上移”，下移最后一项时不提供“下移”；
- 操作依据稳定对象 ID 或执行瞬间的有效位置，不能捕获过期 position；
- 重绑后旧动作被替换或移除，不重复、不串项；
- 排序后焦点仍在被移动对象上，并报告“已移至第 X 项，共 Y 项”。

对复杂列表，优先采用 `AccessibilityDelegateCompat` 的 `onInitializeAccessibilityNodeInfo` 和 `performAccessibilityAction`，或项目架构中经过验证的等价方式。

### 7.4 默认点击、长按与提示

覆盖 `ACTION_CLICK` 或 `ACTION_LONG_CLICK` 的可读标签，只是在告诉用户该标准动作会做什么，不会自动新增一个自定义动作，也不会改变实际业务逻辑。

只有真实点击行为就是“复制”时，才能把点击说明改成“复制”。如果默认点击打开详情，而复制只是附加操作，禁止把默认点击说成复制。可访问名称说明控件是什么；动作标签说明执行该动作会发生什么，两者不得混淆。

长按可以保留为健视用户入口，但重要功能不能只依赖“双击并按住”。必须同时提供普通菜单、按钮或自定义无障碍操作。

### 7.5 拖动和复杂手势替代

拖动排序至少提供“上移”和“下移”；长列表应再考虑“移到开头”“移到末尾”或“移动到指定位置”。滑动删除提供“删除”操作，滑动归档提供“归档”操作，双指缩放提供可操作的放大、缩小或数值入口。

执行后优先通过节点值、列表位置、状态更新和标准无障碍事件让服务感知变化。`announceForAccessibility` 或其他命令式播报只能按目标 Android 版本审慎作为补充；不得重复 TalkBack 已经会读出的内容，也不得成为结果唯一来源。

### 7.6 Compose 特别规则

- 使用 Material/Foundation 组件自带语义，不随意清除。
- `mergeDescendants`、`clearAndSetSemantics` 和自定义 `traversalIndex` 会显著改变无障碍树，使用前必须检查合并树和未合并树并真人测试。
- 自定义绘制组件必须为每个有意义的虚拟对象提供语义、边界、状态和操作；无法做到时提供标准组件构成的等价界面。
- 弹窗、底部面板等窗格使用适当 `paneTitle`；重要但非紧急的动态消息通常使用 polite live region；高频内容禁止持续播报。
- 自动化测试同时覆盖关键语义属性和操作，但不能代替 TalkBack 实测。

### 7.7 Android 系统流程

权限、文件选择、分享、通知设置、登录、支付和系统确认流程必须从应用入口到系统页面再返回完整测试。应用不得把重要说明只放在权限弹窗出现之前的一闪而过页面，也不得因从系统页面返回而丢失焦点或任务状态。

### 7.8 Android 强制实测

开启 TalkBack，至少完成：

- 线性向前、向后浏览全部有意义对象；
- 探索触摸不出现大量空白、重复或错误对象；
- 标准激活、返回、滚动、编辑文本和选择项目；
- TalkBack 操作菜单或导航控制中的自定义操作；
- 删除、排序、弹窗、错误、加载和完成后的焦点与反馈；
- 屏幕旋转、前后台切换、列表复用和数据刷新；
- 项目适用时的外接键盘、Switch Access 和 Voice Access。

## 8. iOS 与 iPadOS 应用专项要求

### 8.1 UIKit 与 SwiftUI

优先使用标准 UIKit 或 SwiftUI 控件。UIKit 自定义界面通过 `UIAccessibility`、`UIAccessibilityElement`、traits、value、hint、容器、操作和通知提供信息；SwiftUI 使用框架的 Accessibility 修饰器、语义组合、焦点和操作 API。

- `accessibilityLabel` 说明对象是什么；`accessibilityValue` 说明当前值或状态；`accessibilityHint` 只在结果不明显时说明行为。
- traits 必须符合真实控件，例如按钮、标题、链接、已选择或可调整，不得把所有可点对象都只标成按钮。
- 可调整控件实现标准增减操作；可滚动容器正确报告页码或位置；关闭临时界面支持适用的 escape 行为。
- 不把多个独立任务过度组合成一个 VoiceOver 焦点；也不让装饰子视图产生重复焦点。

### 8.2 VoiceOver 自定义操作

列表项的次级操作可使用 `UIAccessibilityCustomAction`，VoiceOver 可通过“操作”转子访问。SwiftUI 使用 `accessibilityAction` 或 `accessibilityActions`。

UIKit 示例：

```swift
messageView.accessibilityCustomActions = [
    UIAccessibilityCustomAction(name: "复制") { _ in
        copyMessage(messageID)
        return true
    },
    UIAccessibilityCustomAction(name: "删除") { _ in
        requestAccessibleDeleteConfirmation(messageID)
        return true
    }
]
```

SwiftUI 示例：

```swift
MessageRow(message: message)
    .accessibilityAction(named: Text("复制")) {
        copyMessage(message.id)
    }
    .accessibilityAction(named: Text("删除")) {
        requestAccessibleDeleteConfirmation(message.id)
    }
```

自定义操作不得替代错误的默认激活行为。操作数组随对象状态更新，复用单元格不得残留上一对象的动作。执行后更新标准值、状态或布局；必要时才发送适当的无障碍通知。

### 8.3 焦点与通知

- 新屏幕占据主要区域时使用符合平台语义的 screen change；局部布局变化使用 layout change。
- 只有确有必要时才指定通知后的目标元素，避免强制移动 VoiceOver 焦点。
- 普通状态优先由可见且可访问的状态区域、控件值和标准事件表达；announcement 不得滥用。
- 弹窗、sheet、导航返回、删除列表项和刷新后恢复合理焦点。

### 8.4 输入与系统设置

- VoiceOver 手势可以完成全部核心任务；不得要求精确拖动、只靠视觉发现的边缘手势或直接触摸区域。
- iPadOS 和生产力类应用应按项目需求支持外接键盘与 Full Keyboard Access，并避免与系统及 VoiceOver 命令冲突。
- 尊重 Dynamic Type、粗体文本、增强对比度、减少动态效果、字幕和系统音量；文字放大后不得截断关键操作。
- 系统照片、文件、权限、分享、支付和登录流程必须连同返回后的焦点一起测试。

### 8.5 Apple 移动端强制实测

使用真实设备或项目认可的设备组合开启 VoiceOver，完成线性浏览、转子、标准激活、自定义操作、返回、编辑、选择、滚动、错误修正、动态更新和弹窗焦点测试。项目适用时再测试 Switch Control、Voice Control、Full Keyboard Access 和 Accessibility Inspector；自动审计不能替代 VoiceOver 真人任务测试。

## 9. macOS 与 Linux 桌面专项要求

### 9.1 macOS

优先使用标准 AppKit 或 SwiftUI 控件。自定义 AppKit 控件使用与角色对应的 `NSAccessibilityProtocol`，提供属性、操作和通知；自定义操作使用 `NSAccessibilityCustomAction`。旧式键值 `NSAccessibility` API 不是新实现的首选。

- 窗口、工具栏、侧栏、表格、outline、菜单和 sheet 遵循 macOS 键盘惯例。
- 所有功能可通过键盘和 VoiceOver 命令完成；自定义快捷键不得覆盖系统和 VoiceOver 命令。
- 自绘视图要提供完整无障碍子树、位置、命中、状态、值、操作和变化通知。
- 使用 VoiceOver 与 Xcode Accessibility Inspector 测试；Inspector 通过不等于任务通过。

### 9.2 Linux

开始前明确发行版、桌面环境、显示系统、GTK/Qt 版本和 Orca 版本。GTK 使用 `GtkAccessible` 并经 AT-SPI 暴露角色、属性、状态、关系和操作；Qt 使用内置可访问控件，定制控件通过 `QAccessibleInterface` 等标准机制接入 AT-SPI。

- 优先 GTK/Qt 标准控件；自绘、OpenGL 和 Canvas 界面是高风险方案。
- 验证运行环境确实启用并打包了 AT-SPI 依赖，不得只在开发机“看起来能用”。
- 保证 Orca 可读名称、角色、状态、文本、表格和动态变化，且全程键盘可操作。
- 不同桌面环境的键盘惯例和焦点实现可能不同，只有目标环境实测结果可以作为交付证据。

## 10. 跨平台框架与高风险界面

Electron、Tauri、Qt、Flutter、React Native、.NET MAUI、游戏引擎和其他跨平台框架只是一层实现工具，不会自动保证各平台无障碍一致。选型前必须分别验证目标平台的：

- 标准无障碍树桥接；
- 原生控件角色、名称、状态、值和操作；
- 文本编辑、选择、组合框、列表、表格和弹窗；
- 键盘、读屏焦点、系统缩放和高对比度；
- 目标最低系统版本、运行库和打包方式；
- 第三方控件升级后的回归风险。

自绘、Canvas、WebGL、OpenGL、游戏式 UI、节点图、流程图、地图、代码编辑器、远程桌面和虚拟化数据网格属于高风险组件。采用前必须比较：标准组件、成熟可访问组件、结构化等价界面和完全自制实现。未经用户确认，不得为视觉效果锁定高风险架构。

## 11. 安装、更新、迁移、修复与卸载

- 从第一个窗口或第一条终端提示开始，所有步骤都必须可访问。
- 每步有标题、说明、当前步骤和准确按钮名；许可协议是可逐行阅读、选择和复制的真实文本。
- 安装路径、组件、快捷方式、自动启动、遥测和隐私选项有标签及状态。
- 进度、完成、失败、重启和回滚可读；不能只显示动画或关闭窗口。
- 更新前验证新版本继续支持目标系统，且没有无障碍退化。
- 更新失败保留原可用版本或提供可访问恢复；迁移前说明备份、不可逆变化和回退方式。
- 卸载可全键盘或读屏完成，并明确哪些用户数据、设置、缓存和日志会保留或删除。
- 禁止静默安装未选择的软件、修改无关系统设置或在后台抢焦点。

## 12. 命令行、终端与服务器管理

### 12.1 命令行输出

- `--help` 或等价入口列出用途、语法、参数、默认值、环境变量、退出码和示例。
- 输出使用真实 Unicode 文本和普通行，可逐字逐行朗读、选择、复制和重定向。
- ANSI 颜色、图标、表格边框、光标移动、动画进度条或全屏 TUI 不得作为唯一信息。
- 若提供交互式 TUI，必须同时提供行模式、普通子命令或非交互参数，完成相同核心任务。
- 重要表格提供 TSV、CSV、JSON 或无边框文本模式；不要只靠列对齐表达关系。

### 12.2 状态与错误

- 长任务输出节制且清楚的阶段、进度和最终结果，必要时提供 `--quiet`、`--verbose`、日志文件或机器可读模式。
- 提示在等待输入前先说明需要输入什么、允许值和取消方式。
- 成功退出码为 0，失败为非 0；错误写入适当输出流并包含可执行的修复建议。
- `Ctrl+C` 可取消，并说明是否留下部分结果、锁文件或临时资源。
- 密码和密钥不回显、不进入 shell 历史建议、不写普通日志。

### 12.3 服务器产品

服务器核心可以是无界面服务，但必须保证管理入口可访问：

- 管理网页执行第 6 节；
- 管理客户端执行对应桌面或移动章节；
- CLI 和 SSH 工作流执行本节；
- API 文档有语义标题、代码文本、可复制示例和清楚错误结构；
- 监控和告警不以颜色、图形或声音作为唯一严重级别；
- 日志明确时间、时区、级别、对象、操作、结果和关联 ID，并可导出纯文本或结构化格式。

## 13. 图片、图表、地图、媒体、文档与数据

- 信息图片有准确文字替代；装饰图片从无障碍树隐藏；图片内重要文字另给真实文本。
- 图表提供标题、结论摘要、关键数值和完整可访问数据表或下载。
- 颜色、线型、位置、大小和视觉趋势不得成为唯一信息。
- 地图、流程图、画布和节点图提供结构化列表、表格、步骤文本或等价键盘界面。
- 视频关键视觉信息提供音频描述、文字说明或等价内容；播放、暂停、进度、音量、速度、字幕和全屏控件有名称及标准操作。
- 声音不得自动播放且无法立即停止，以免盖住读屏。
- 导出文本可选择和复制，并保留标题、列表、链接和表格结构。
- 若 PDF 无法保证目标环境可访问，同时提供 HTML、TXT、DOCX、CSV 或其他适合内容的可访问格式。

## 14. 读屏专用接口、OCR 与 AI 描述政策

普通软件和网页的主要实现必须使用平台标准无障碍树和事件：Windows UIA、Web Accessibility Tree、Android Accessibility、Apple UIAccessibility/NSAccessibility、Linux AT-SPI 等。

争渡专用 API、TalkBack 特定技巧、VoiceOver 私有假设、读屏插件、OCR、自动标签和屏幕识别均不得成为核心信息唯一来源。只有具体项目明确要求时，才评估专用接口；它必须是可关闭增强，不能重复标准朗读、频繁打断或破坏其他读屏。

OCR 和 AI 图片描述适合用户主动发起的未知内容辅助，不适合代替开发者能够确定提供的标签、文本、结构和状态。

## 15. 开发流程与代码修改规则

### 15.1 开发前

1. 建立平台和版本矩阵。
2. 列出核心用户任务，而不只是页面清单。
3. 为每个任务写出输入方式、焦点路径、结果反馈、错误恢复和取消路径。
4. 检查框架与第三方组件的标准接口；对复杂编辑器、网格、WebView、拖放、图表和自绘组件先做最小验证原型。
5. 记录不可逆选型、替代方案、假设和失败预算。

### 15.2 编码中

- 功能代码与无障碍语义、键盘或手势、焦点恢复和测试同时提交。
- 每完成一个窗口、页面或核心流程立即验证，不等全部完成后才开读屏。
- 所有可视入口和无障碍自定义操作调用同一业务层。
- 新增状态时同时更新可访问值和事件；删除节点前先确定后续焦点。
- 不为通过自动扫描而添加虚假名称、错误角色或隐藏真实问题。
- 修改已有项目时，至少回归受影响流程及其前后相邻步骤；不破坏原有快捷键和读屏习惯。

### 15.3 代码审查必须问

- 这个功能不用视力能否发现？
- 不用鼠标或精确拖动能否完成？
- 对象的名称、角色、状态、值和操作是否与真实行为一致？
- 变化是否通过标准语义和事件提供？
- 焦点打开后去哪、关闭后回来哪里、删除后落在哪里？
- 列表复用、异步加载、失败重试和权限变化会不会产生旧状态？
- 是否制造了大量重复焦点，或反过来隐藏了独立功能？
- 是否把专用播报、OCR 或自动扫描当成了完成证据？

## 16. 强制验收与失败门槛

### 16.1 验收原则

人工任务测试是最终依据。自动扫描、单元测试、UI 测试和无障碍树检查用于发现回归，但不能证明读屏用户能完成任务。

测试必须记录：环境、版本、设备、读屏、输入方式、步骤、期望、实际结果、通过或失败、缺陷复现方式。未经实际测试的组合必须列为“未测试”，不得写“兼容”。

### 16.2 通用真实任务

按项目实际覆盖：

- 安装、首次启动、授权、注册或登录；
- 识别窗口或页面标题、主要区域和当前位置；
- 新增、打开、查看、编辑、保存、取消和删除；
- 搜索、排序、筛选、分页、上传、下载、导入和导出；
- 菜单、上下文操作、设置、帮助、弹窗和多窗口；
- 触发错误、修正字段、重试、取消长任务；
- 检查加载、进度、部分成功、成功和失败；
- 关闭弹窗、返回页面、删除项目和刷新后核对焦点；
- 重启后确认数据、设置和恢复状态；
- 存在时测试更新、回滚、修复和卸载。

### 16.3 控件逐项核对

核对名称、角色、状态、值、单位、范围、位置、禁用、只读、必填、无效、展开、选中、标准操作、焦点顺序、变化事件和操作结果。虚拟列表、表格和自定义控件必须检查滚动或复用后的节点是否仍然正确。

### 16.4 一票否决项

出现任一情况，核心验收失败，项目不得宣称完成：

- 桌面或网页核心任务必须使用鼠标、模拟鼠标、屏幕坐标、OCR、标签或路标；
- 移动端核心任务必须依赖精确点按、不可替代拖拽、视觉路径或无法被读屏发现的手势；
- 核心控件读成未知、空白、无意义名称或错误类型；
- 状态、值、错误、进度或结果无法得知；
- 焦点丢失、乱跳、进入隐藏对象、被后台抢走或无法离开；
- 重要弹窗、系统权限、错误、进度、确认或完成结果不可读；
- 列表复用导致动作串项、操作旧数据或焦点对象变成别的项目；
- 快捷键与系统、浏览器或读屏冲突且没有替代入口；
- 当前承诺的最低系统不能安装、启动或完成核心任务；
- 安装、更新、迁移、修复或卸载包含不可访问步骤；
- 要求用户安装读屏专用补丁才能弥补产品缺陷；
- 仅凭自动扫描、代码推断或 AI 自述就声称真人读屏验收通过。

## 20. 最终原则

先保证盲人用户本人能够在目标环境独立完成任务，再扩大兼容范围；先保证标准无障碍树，再考虑读屏专用增强；桌面和网页先保证纯键盘完整可用，移动端先保证读屏焦点、标准激活和可发现操作完整可用；先选择标准控件和语义结构，再考虑自定义视觉界面。

无障碍、稳定性、数据安全和已承诺的最低系统兼容性都是核心功能。任何功能只要必须依赖视力、OCR、屏幕坐标、读屏补丁或他人帮助，就不能算完成。
